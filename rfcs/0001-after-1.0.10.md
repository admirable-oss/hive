# RFC 0001: The roadmap after 1.0.10

- **Status:** Proposed. Open for comment; the council decides after the
  discussion period ([process](README.md#process)).
- **Authors:** the maintainers
- **Discussion:** the pull request that adds this file
- **Affects:** [ROADMAP.md](../ROADMAP.md)

## Summary

The 1.0 train (M10 to M19) added the plugin store, images, Windows,
observers, the web and mobile observers, local discovery and the desktop
app. M19 then reviewed it for release quality. This RFC proposes what comes
next. First, close the gaps the train left open, so that 1.0.x is
dependable and the desktop app can leave preview. Then, for 1.1, two
directions from *Beyond v1.0.10*: parallel agent orchestration and
Git-native development. Hosted, fleet and team features wait for an RFC of
their own and signs of demand.

**We are asking for comment** on the order, on what is missing, and on the
open questions at the end.

## What we observed

Hive sends no telemetry, so this is what can be seen without it:

- **Releases.** Only `v1.0.0-rc.1` is tagged. M10 to M18 are on `main`
  untagged, so users of the stable channel have no 1.0 release yet. This is
  the largest gap between the roadmap and what users can install.
- **Plugins.** The registry lists two official plugins. Their release tags
  share hive's tag namespace, and the official catalog is not seeded with
  installable releases (M10's open items).
- **The desktop app** works and is tested, but its packages are not signed,
  and it has no in-app update or measured latency in the native webviews
  (M18's open items).
- **Reliability.** The nightly soaks, budgets and fuzzing pass. The 72-hour
  chaos gate and a cross-user connection test need a self-hosted runner,
  which does not exist yet.
- **Security.** The M19 review fixed ten findings and left six open items
  ([docs/security-review.md](../docs/security-review.md)).

## Proposal

### 1. Finish 1.0.x: dependable releases (1.0.10 to 1.0.x)

1. **Tag the train.** Cut `v1.0.10` from `main` as the first stable 1.0
   release, once M19's release checklist
   ([GOVERNANCE.md](../GOVERNANCE.md#releases)) passes. Users on
   `v1.0.0-rc.1` upgrade straight to it; the upgrade test covers that path.
2. **A self-hosted runner** for the 72-hour chaos soak, the cross-user peer
   check, and long multi-machine soaks.
3. **Official plugins in their own repository**, released and seeded in the
   catalog, with per-plugin tags.
4. **Installer signature checks** (`install.sh`, `install.ps1`), so the first
   install is verified like every update.

### 2. The desktop app leaves preview (1.1)

Developer ID signing and notarization, Windows code signing, signed Linux
packages, the Homebrew cask, in-app updates that verify the release
signature and keep the previous version, and latency, CPU and memory
measured in the native webviews. Then the app is covered by the
compatibility policy.

### 3. Parallel agent orchestration (1.1)

From *Beyond v1.0.10*: run sets of agents on independent tasks, with
dependencies, concurrency and resource limits, completion conditions and
structured results, while sensitive operations still ask a human. It builds
on what agents already use (`hive agent start --worktree`, `prompt --wait`,
MCP) and would add a task model to the wire API, which needs its own RFC.

### 4. Git-native development (1.1)

Branch lifecycle for agent worktrees, conflict detection between agents'
branches, review workflows, cleanup policies, and validation (tests, lint)
before changes are proposed. The developer keeps every commit, merge and
push.

### 5. Later, each with its own RFC

Hosted foundations, runtime fleet management, team collaboration and
workflow automation stay in *Beyond*. Each needs an RFC that shows who asks
for it, and how the self-hosted product keeps working without it.

### Not proposed

- No breaking changes in 1.x. Nothing is planned for removal before 2.0.
- No telemetry. If usage data is ever wanted, it needs an RFC, and opt-in.

## Compatibility

Everything proposed is additive. The orchestration task model and any
registry schema change for per-plugin tags need their own RFCs. A registry
schema change in particular must keep releases before 1.0.10, which reject
unknown catalog fields, working (see
[docs/compatibility.md](../docs/compatibility.md#plugins)).

## Open questions

1. **Tagging.** Should the train be released as `v1.0.10` directly (the
   proposal, matching the roadmap's labels and these docs), or as `v1.0.0`
   with the milestones following as patches?
2. **Order.** Is orchestration or Git-native more useful first, or should
   1.1 be the desktop app alone?
3. **What is missing?** Which problems running agents with Hive are not on
   this list? Plugin authors: what does plugin API 1 lack?
4. **Windows arm64.** Is it wanted enough to add once CI can run it?
